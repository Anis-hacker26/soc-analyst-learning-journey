# 🖥️ Windows Event Viewer

## Introduction

Windows Event Viewer is a built-in Microsoft tool that records and displays important events generated by the Windows operating system, applications, drivers, and security components.

It provides a centralized location for viewing system activity, troubleshooting problems, monitoring security events, and investigating incidents.

For Security Operations Center (SOC) analysts, Event Viewer is one of the primary sources of evidence during incident investigations because it records authentication events, system changes, application errors, and many other security-related activities.

# Windows Event Logging Architecture

Windows follows an event-driven architecture. Whenever an important activity occurs, the responsible Windows component generates an event.

The Windows Event Log service collects these events, stores them in log files, and makes them available through Event Viewer.

```
User / Application / Windows Component
                │
                ▼
        Event Generated
                │
                ▼
   Windows Event Log Service
                │
                ▼
      Event Log (.evtx)
                │
                ▼
      Windows Event Viewer
                │
                ▼
         SOC Investigation
```

### Key Takeaway

Event Viewer **does not create events**. It only displays events that have already been recorded by the Windows Event Log service.

# Windows Event Logs

Windows organizes events into different log categories based on the component responsible for generating the event.

## Application Log

### Purpose

Records events generated by applications.

### Examples

- Application crashes
- Runtime errors
- Database events
- Software updates

### Investigation Question

> What did the application do?

---

## Security Log ⭐

The Security log is one of the most important logs for SOC analysts.

### Examples

- Successful logins
- Failed logins
- Account lockouts
- Password changes
- User creation
- Privilege changes

### Investigation Question

> Who performed the action?

---

## System Log ⭐

Records events generated by Windows itself.

### Examples

- Driver loading
- Service startup
- USB connection
- Hardware failures
- Network adapter events

### Investigation Question

> What happened to the operating system?

---

## Setup Log

Records Windows installation and update events.

### Examples

- Windows installation
- Feature updates
- Driver installation

### Investigation Question

> What happened during Windows setup or updates?

---

## Forwarded Events

Contains logs collected from remote Windows systems using Windows Event Forwarding.

This is commonly used in enterprise environments where multiple computers send their logs to a central server.

---

# Event Levels

Windows assigns a severity level to every event.

## Information

Normal operating activities.

Examples:

- Service started
- Successful process execution
- Normal application activity

---

## Warning

Potential problems that may require attention.

Examples:

- Low disk space
- Delayed service response

---

## Error

An operation failed.

Examples:

- Service crash
- Driver failure
- Application failure

---

## Critical

Serious system failures.

Examples:

- Unexpected shutdown
- Kernel failure

---

## Audit Success

Security operation completed successfully.

Examples:

- Successful login
- Access granted

---

## Audit Failure

Security operation failed.

Examples:

- Wrong password
- Account lockout
- Access denied

---

# Important Note

Event Level **does not indicate whether an activity is malicious**.

For example:

PowerShell starting may appear as an **Information** event, but depending on the parent process and command line, it could still require investigation.

SOC analysts investigate **context**, not just event levels.

---

# Event Providers

Every event is generated by a specific Windows component known as a Provider.

Examples include:

- Microsoft-Windows-Sysmon
- Microsoft-Windows-Security-Auditing
- Service Control Manager
- Windows Defender

The Provider determines the meaning of an Event ID.

---

# Event IDs

An Event ID identifies a specific event **within a particular provider**.

For example:

Provider:

```
Microsoft-Windows-Sysmon
```

Event ID:

```
1
```

Meaning:

```
Process Creation
```

However, Event ID **1** from another provider may represent a completely different event.

### Key Takeaway

Always identify the **Provider first**, then interpret the Event ID.

---

# Event Details

Every event contains two primary views.

## General

Displays a human-readable explanation of the event.

Best used for:

- Initial investigation
- Understanding event summaries

---

## Details

Displays structured event data.

Includes:

- XML format
- Event fields
- Provider information
- Raw event data

Best used for:

- SIEM ingestion
- Detection engineering
- Automation
- Advanced investigations

---

# XML View

The XML representation contains the complete event structure.

This format is commonly used by:

- Splunk
- Microsoft Sentinel
- Sigma Rules
- Detection Engineering
- Automated log processing

---

# Event Filtering

Large environments generate thousands of events every day.

Instead of manually reviewing logs, Event Viewer allows filtering by:

- Event ID
- Level
- Date
- Provider
- Keywords
- User

Filtering enables analysts to quickly locate relevant evidence during investigations.

---

# Windows Event Viewer vs Sysmon

| Windows Event Viewer | Sysmon |
|----------------------|---------|
| Displays Windows events | Generates additional security events |
| Built into Windows | Requires installation |
| Focuses on operating system logging | Focuses on security telemetry |
| Stores Windows logs | Extends Windows logging |

Sysmon events are also stored inside Windows Event Logs and can be viewed through Event Viewer.

# SOC Investigation Workflow

Rather than memorizing Event IDs, investigations should follow a structured process.

```
Incident Reported
        │
        ▼
What happened?
        │
        ▼
Is the activity normal?
        │
        ▼
Which Windows component is involved?
        │
        ▼
Which log should contain evidence?
        │
        ▼
Which Provider generated the event?
        │
        ▼
Which Event ID is relevant?
        │
        ▼
Review General and Details
        │
        ▼
Analyze Context
        │
        ▼
Conclusion
```
